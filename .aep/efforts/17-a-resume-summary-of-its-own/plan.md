# Architecture

The root cause is a modelling one. `summary` was specified as a property of the person, and it is read by four outputs of which one is a document with a page budget. Effort 15 tried to write one text that served the CV and the resume at once and produced one that served neither, which is what a single field forces once the two documents stop carrying the same entries.

**The fix keeps the summary a property of the person and adds a second one, rather than re-keying the first by document.** `summary` keeps its name, its schema shape, and every consumer it has. A required `resumeSummary` sits beside it and is read by exactly one caller.

The seam this cuts at already exists. `src/components/CvDocument.astro` resolves its `variant` prop into `const resume = variant === 'resume'` at line 62 and already uses it to choose the projects list, the education detail, the skills layout, and the order of the tail sections. Choosing the summary on the same boolean adds a branch to a component whose whole job is branching on that boolean, and adds no new concept to it.

## Alternatives, and why they lost

**One `summary` keyed by document**, as `summary.cv` and `summary.resume`. Symmetric, and it would make a third document impossible to add without deciding its summary. It lost on naming: `summary` is read by `src/lib/resume.ts`, `src/pages/[locale]/index.astro`, `scripts/readme-profile.mjs`, and the CV, and only the last of those is the CV. A key called `cv` would be false for three of its four readers, and any honest name for it (`long`, `default`, `site`) reintroduces the asymmetry the shape was chosen to remove while still costing five consumers a change to print the text they already print. Saud chose against it on 2026-09-11.

**Optional, falling back to `summary` when absent.** Rejected on 2026-09-11 because it makes the defect this effort exists to fix the default. A later edit that dropped the field would restore the shared paragraph on the resume silently, and silence is how it got there the first time. There is one profile in the repository, so requiring the field costs no migration.

**A second component for the resume.** Named only to close it off. `CvDocument.astro` exists so the two documents cannot drift in layout, which is stated in its own header comment, and splitting it to vary one paragraph would trade a one-line ternary for a second template and the drift it invites.

# Components

| File | What changes | What it becomes responsible for |
| --- | --- | --- |
| `src/content.config.ts` | the profile schema gains `resumeSummary: localized`, required, beside `summary` | refusing a profile that has no resume summary, at build time |
| `src/content/profile.yaml` | `resumeSummary` authored in both languages; `summary` loses its Nova clause in both; the comment above them rewritten | holding both texts, and saying which document each reaches and why they differ |
| `src/components/CvDocument.astro` | the `summary` const becomes a choice on the existing `resume` boolean | being the one place that decides which summary a document prints |
| `README.md` | the profile block, regenerated by `pnpm readme` | nothing new; it follows `summary` as it already does |
| `src/content/README.md` | the `profile.yaml` field table gains a row, and the `summary` row says which outputs it reaches | telling the next editor which document they are editing |
| `tests/resume.spec.ts` | an assertion per document that it prints its own summary | catching a document that drifts from the field it is supposed to read |
| `scripts/check-dist.mjs` | `jsonResume` gains an assertion that `basics.summary` is the authored `summary` | closing the one output whose summary nothing checks today |

Untouched, and deliberately: `src/lib/resume.ts`, `src/pages/[locale]/index.astro`, `scripts/readme-profile.mjs`, `tests/home.spec.ts`. Spec requirement 4 says nothing else changes what it shows, and under this approach that is guaranteed by the shape rather than by care, because none of those files can see the new field.

# Data model

```
profile:
  name          localized
  label         localized
  summary       localized   the CV, the home page hero, README.md, both resume.json
+ resumeSummary localized   the resume, and nothing else
  email         email
  nationality   localized
  location      localized
  profiles      list
```

`localized` is the existing helper in `src/content.config.ts`: `en` required, `ar` optional and falling back to English with the gap recorded. `resumeSummary` uses it unchanged, so the new field arrives already covered by both gap reporters. The build's reporter in `src/lib/localized.ts` records a gap when the Arabic resume renders, and the static walker in `check-dist.mjs`'s `gaps` check recurses the profile generically and needs no change to see a new key.

# Technical approach

The order, and what forces it:

1. **The schema and the content together, in one change.** The field is required, so a schema that requires it and a `profile.yaml` that lacks it is a tree that does not build. They land in the same commit or every state in between is broken.
2. **`CvDocument.astro` reads it.** After 1, because the component cannot reference a field the schema has not declared without a type error from `pnpm check`.
3. **The CV summary loses the Nova clause, and `pnpm readme` regenerates the README block.** One change, because the README block is generated from that field and `check:dist` fails when it is behind. Independent of 1 and 2, since it touches the other field.
4. **`src/content/README.md` gains the row.**
5. **The test and the dist assertion.**
6. **Measure.** `pnpm render:pdf` last, because it measures the finished document.

## What the implementer writes, and what is already decided

So that no paragraph gets rewritten that was not asked for:

- **The CV summary loses the Nova clause and nothing else.** Its third sentence keeps the PL/0 compiler and the Monkey interpreter; only the statically typed language on a bytecode virtual machine comes out, in both languages. `cachescribe`, PL/0, and `monkey-lang` are all `public` and `completed`, so all three print as entries on the CV, on the work page, and in both JSON documents, and their clauses are checkable against the record.
- **The resume summary is two or three sentences**, as `src/content/README.md` sets for a summary of this kind. It names `rentable` and Mudaraj and no other project, and it calls Mudaraj a prototype built for a bachelor's senior project, claiming no more than the role line in `src/content/projects/mudaraj.yaml` already states.
- **It may reuse the rentable clause the CV summary carries.** The two documents are read separately and the same sentence is true on both; there is no requirement that they be worded differently.
- **The Arabic mirrors the English sentence for sentence**, as the existing pair does.

# Testing strategy

Each acceptance criterion in `spec.md`, against the thing that checks it:

| Criterion | Checked by |
| --- | --- |
| schema requires the field; one selection site | `pnpm check` fails on a `profile.yaml` without it, confirmed once by hand by removing the field and restoring it; the diff shows one `resumeSummary` read in `src/` |
| resume summary names `rentable` and Mudaraj only | the new `tests/resume.spec.ts` assertion proves the document prints the authored field; **what is authored is checked by review**, because a string blacklist over a paragraph would pass on a synonym |
| Mudaraj named as a prototype for a bachelor's senior project, entry untouched | `git diff --stat` shows `src/content/projects/mudaraj.yaml` absent; the wording by review against that file's role line |
| `summary` drops Nova, keeps the npm package, PL/0, and Monkey | the new assertion that the CV page prints `summary`; the text by review |
| home hero and both `resume.json` carry the edited `summary` | `tests/home.spec.ts:159`, which already reads `profile.summary[locale]` and follows automatically; the new `basics.summary` assertion in `jsonResume`; `check:dist` reporting `readme profile` |
| `[localized] 0 gaps` and the gates | `pnpm build`, `pnpm check`, `pnpm check:dist`, `pnpm test`, `pnpm test:content` |
| the content README documents both fields | review |
| one page, at or above the 10mm floor | `pnpm render:pdf`, both languages, both papers, published and filled, with the free height at Letter recorded in the commit |

**New coverage this adds.** Nothing today asserts that either document prints the profile summary at all, and nothing asserts `basics.summary` against the source. `tests/resume.spec.ts` is the right home for the first: it already parses `src/content/profile.yaml` directly and exists to assert the part where the two documents differ. `jsonResume` in `check-dist.mjs` is the right home for the second, beside the `basics.url` assertion that is already there.

**No fixture change.** `scripts/test-content-mechanism.mjs` writes a project and a certificate and never touches `profile.yaml`, so a new required profile field does not reach it.

# Technical risks

- **The schema and the content have to land together.** Separating them gives a commit that does not build. It shows up immediately, as a Zod failure naming `resumeSummary`, and the mitigation is step 1 of the order above.
- **The Arabic resume summary is the one thing no gate can judge.** Both gap reporters check that Arabic exists, not that it says what the English says. Spec requirement 6 is a review criterion, as it was for every localized field before it.
- **The measurement moves the wrong way and nobody notices.** The new paragraph drops four projects and adds one, so the resume should gain headroom against the 15.4mm effort 15 left. If it comes back lower, something other than the summary changed, and the number in the commit is what makes that visible rather than a pass on the floor.
